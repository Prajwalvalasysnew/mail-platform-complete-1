# Valasys AI writing: implementation and operation

This implements the focused writing release: subjects, selected-text rewrite, structured email drafts, and conversational writing assistance in the original `/ai-agent` design. It includes durable conversations, checkpoint compaction, bounded read-only workspace tools and owner-scoped history retrieval. Campaign sending, workflow activation and scheduled routines remain unavailable.

The configured inference host was checked using synthetic data: Ollama 0.14.2 listed `gpt-oss:120b-cloud`, and a structured subject request completed in about 1.4 seconds. The user explicitly authorized that existing cloud model. This is cloud-backed inference behind the configured endpoint, not a verified local 120b deployment. No credentials are stored in committed files.

## Configuration and startup

Apply migrations 105 through 108 through the normal release migration command before starting updated services. Configure the API and separate AI worker with the same AI settings from `.env.example`. Enable only selected tenant UUIDs with `AI_ENABLED_TENANTS`; `*` is an explicit all-tenant option. The ignored local `.env` has the user's approved endpoint/model credentials copied from the existing harness settings for development. Production configuration is separate.

Set `AI_ENABLED=true`, `AI_BASE_URL` to the trusted inference origin, `AI_MODEL` to the exact installed model and `AI_GATEWAY_TOKEN` through secure configuration. Cloud-tagged models additionally require `AI_ALLOW_CLOUD=true`. The URL is never supplied by customer input; redirects and credential-bearing URLs are rejected.

After building shared and worker packages, run `npm run dev:api` and the dedicated worker with `npm run dev:ai` locally, then `npm run dev:customer` for the UI. The root API/AI development commands load the ignored local `.env`; already-exported environment values take precedence. Use `npm run start:ai --workspace=@platform/worker` in an already configured runtime. Compose has an `ai` profile; start `ai-worker` alongside the API after migrations. Helm supports `ai.enabled` and uses the API's non-BYPASSRLS database credential for the worker. Store `AI_GATEWAY_TOKEN` in the existing Kubernetes secret; do not put it in values or a ConfigMap.

The process uses port 9103 for `/live` and `/health`, with no public service required. It has no mail transport credentials. Do not start the normal mail-worker command in the AI container. AI failure does not change API/mail readiness.

## Execution and controls

The human-session API lives under `/v1/account/ai` (browser `/api/account/ai`). Generation requires the existing `send` capability, active customer/user/session, satisfied MFA where applicable, an enabled tenant and bounded validated input. Requests use a client UUID for idempotency; transient submission and polling failures retry at most twice, preserving that UUID; changed input under the same ID conflicts. One active run per user and a per-user daily limit prevent runaway admission. All worker replicas share BullMQ global concurrency; start conservatively at one.

The API commits a tenant/user-owned run then attempts enqueue. The worker's recurring dispatcher recovers missing queue delivery, marks expired runs, and retries at most one interrupted execution before the deadline. Attempts are fenced so stale output cannot overwrite cancellation or another attempt. Model requests have bounded time, context, output and response-body sizes. Queue data contains IDs only; completed runs clear the input snapshot.

The editor polls status using its existing busy controls and subject dropdown. Validated drafts and rewrites appear on the editable canvas for review before Save or Send. No extra overlay or layout was added. A document fingerprint prevents a late response from overwriting edits. The existing Undo action restores the preceding content, subject and preheader. Rewrites preserve exact merge tags and operate on plain text blocks. Draft HTML is rendered from escaped model text and a fixed vocabulary; buttons can use only safe links supplied in the writing input. Preview iframes disallow scripts. Domain checks can block link-domain findings; spam scores are warnings, not inbox-placement promises. The delivery worker remains responsible for the trusted footer and all send-time restrictions.

The AI page retains the original chat, approval cards, navigation and layout. Chat uses actual bounded model responses. A generated email becomes a durable pending draft card. Approval creates a template and version plus the recorded decision in one transaction; retrying the approval returns the same saved template. Its existing Open link loads the editor. Selecting the existing auto-apply-drafts mode explicitly permits saving generated drafts. Chat transcripts are now server-owned and restore after refresh or a new login within the configured retention period. Business notes, skills and mode save with each submitted turn. The worker builds canonical context, automatically compacts older history into fenced checkpoints, supports `/compact`, and retries once after a confirmed context overflow. Raw messages remain stored. Leaving the chat screen detaches polling without cancelling server work; reopening it resumes the existing run. Explicit Stop cancels it. Editor navigation still cancels pending writing rather than applying a stale draft. The original @ context menu now lists actual tenant campaigns, templates, workflows and audiences. Read-only tools retrieve selected records, retained delivery rollups, domain verification and the current user's earlier chat messages. Scheduled routines and mutable account actions remain unavailable and never report simulated execution. It does not send mail. A failed save with an uncertain outcome must be checked in Templates before resubmitting.

## Privacy and retention

Runs are tenant scoped with FORCE RLS plus user ownership in every public lookup. The worker rechecks original session/membership/account authority before inference, during execution and before result commit. Logout/session revocation, organization changes, cancellation and deletion fence completion. The API response contains only product status/result/warnings, never raw prompts, credentials, model names or upstream errors.

Content defaults to a 24-hour expiry and is hidden by the API after expiry. The recurring worker removes expired content/records unless an active tenant legal hold or regulatory retention lock requires retention. Minimal daily quota/idempotency markers survive for at least 24 hours. The account-holder export includes the user's AI writing records; login-session deletion invalidates unfinished run authority while retaining quota records; account deletion removes unheld conversations. Recipient erasure also clears matching free-text AI snapshots/results and prevents pending completion. The caller can export current result records and delete a standalone writing run with the AI endpoints, subject to holds. A chat run must be erased through the conversation deletion endpoint so that transcript and checkpoints are deleted together. Operational deletion/expiry requires the worker to stay running and its health to be monitored.

## Read-only agent execution

The worker can request at most four structured planning rounds and four distinct registered reads. Tool arguments are validated, repeated calls are blocked, SQL is fixed and parameterized, and each read rechecks authority. Reads have a four-second cancellation budget and a three-second SQL timeout. Tool observations are saved with the run attempt under FORCE RLS; the browser receives safe progress labels rather than raw observations. Domain keys, verification tokens and recipient rows are excluded. Workspace content and retrieved messages are untrusted evidence, never executable instructions.

A fixed-density text token estimate adapted from the harness is telemetry only; admission retains the conservative byte budget. Provider transport rejections have one bounded retry; connection failures stop planning immediately and preserve the conversation with a product error. Exact history retrieval is bounded by ownership, retention and excerpt limits; summaries remain lossy.

Use `scripts/ai-grounded-smoke.mjs` with the isolated `mail_test` database, test Redis and an `ai_eval_` queue prefix to validate live delivery facts, selected-template grounding and exact earlier-message retrieval using synthetic records. Set `AI_BROWSER_SYNTHETIC_PROVIDER=true` for deterministic browser testing without hosted inference; omit it to test the approved hosted model. Never confuse deterministic test results with model quality or uptime evidence.
